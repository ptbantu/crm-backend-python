# BANTU CRM V5.0 数据库迁移指南

## 概述

本文档提供了从现有CRM数据库迁移到V5.0新架构的详细步骤和指南。V5.0数据库设计采用了以下核心原则：

1. **统一UUID主键**：所有表使用UUID char(36)主键
2. **无物理外键**：使用逻辑关联替代物理外键
3. **模块化前缀**：使用`sys_`、`crm_`、`exe_`、`fin_`前缀
4. **智能检索集成**：支持全链路智能搜索
5. **业务流程重构**：商机流水线、执行分派、财务结算、审核闭环

## 文件说明

### 核心文件
1. **v5_schema.sql** - V5.0新表结构定义
2. **v5_migration.sql** - 数据迁移脚本（从现有表迁移到新表）

## 迁移策略

根据用户选择，采用以下策略：
- **一次性迁移**：在维护窗口内一次性完成数据迁移
- **分模块渐进**：按模块逐步上线，每个模块独立部署
- **Redis Search**：智能检索使用Redis Search

## 数据迁移详细说明

### 客户表迁移（关键难点）

现有`customers`表使用自增整数ID，新表`crm_customers`使用UUID。解决方案：

1. **ID映射表**：创建临时映射表记录新旧ID对应关系
2. **外键更新**：使用映射表更新所有相关表的外键
3. **视图兼容**：创建视图保持API兼容性

```sql
-- ID映射表示例
CREATE TEMPORARY TABLE customer_id_mapping (
    old_id INT PRIMARY KEY,
    new_id CHAR(36) NOT NULL
);

-- 填充映射表
INSERT INTO customer_id_mapping (old_id, new_id)
SELECT c.id, UUID() FROM customers c;
```

### 迁移验证脚本

迁移后需要执行验证脚本检查数据完整性：

```sql
-- 验证客户迁移完整性
SELECT
    '客户表' as table_name,
    (SELECT COUNT(*) FROM customers) as old_count,
    (SELECT COUNT(*) FROM crm_customers) as new_count,
    CASE
        WHEN (SELECT COUNT(*) FROM customers) = (SELECT COUNT(*) FROM crm_customers)
        THEN '通过'
        ELSE '失败'
    END as status;
```

## 回滚方案

### 回滚触发条件
1. 数据丢失或损坏
2. 性能严重下降
3. 关键功能失效
4. 用户投诉率超过阈值

### 回滚步骤
1. 立即停止新系统流量
2. 切换回旧系统
3. 使用备份恢复数据
4. 分析失败原因

### 回滚脚本使用
```sql
-- 1. 备份新表数据
-- 2. 执行v5_rollback.sql中的备份部分
-- 3. 验证备份完整性
-- 4. 根据情况选择回滚选项
```

## 风险与缓解措施

### 高风险：数据丢失
- **缓解**：完整备份，分阶段验证
- **监控**：实时监控数据一致性
- **回滚**：准备快速回滚方案

### 中风险：性能下降
- **缓解**：性能测试，索引优化
- **监控**：APM监控关键指标
- **优化**：查询优化，缓存策略

### 低风险：功能不兼容
- **缓解**：API版本控制，兼容视图
- **测试**：全面回归测试
- **沟通**：提前通知用户

## 附录

### 常见问题解答

#### Q1: 迁移期间系统需要停机吗？
**A**: 建议在低峰期进行一次性迁移，预计需要4-8小时停机时间。

#### Q2: 如何验证迁移数据的正确性？
**A**: 使用迁移脚本中的验证部分，检查数据数量、关联关系和业务逻辑。

#### Q3: 迁移失败怎么办？
**A**: 立即执行回滚计划，恢复旧系统，分析问题原因。

#### Q4: 新旧系统能否并行运行？
**A**: 可以，通过双写策略和API适配层实现，但会增加系统复杂度。

#### Q5: 用户需要重新培训吗？
**A**: 对于基础功能不需要，新功能需要适当培训。
